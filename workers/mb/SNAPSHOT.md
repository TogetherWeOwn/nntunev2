# R2 snapshot backend — phase 0 spike

Measurement-only. Every deployed `workers/mb` environment leaves
`MB_BACKEND` unset and keeps the Hyperdrive repository; nothing here
changes the `/v1/mb/*` contract or any production configuration.

The question: can an immutable snapshot of the curated CC0 subset in R2,
read through `SnapshotRepo` (`src/snapshot.rs`) behind the existing
`MbRepo` trait, replace the PlanetScale `nntunev2-mb` cluster?

That cluster was deleted on 2026-11-06 (it held only a test seed), so the
`pg_trgm` baseline runs on a throwaway Postgres container inside the
spike job. A no-go would mean recreating the cluster, which is new spend
and an owner decision first.

| Piece | Where |

| Snapshot builder / local read path | `examples/snapshot_build.rs`, `examples/snapshot_eval.rs` |

| Orchestration | `.github/workflows/mb-snapshot-spike.yml` |

## Format

Per kind (`artist`, `release`, `recording`, `release-search`) under
`snap/<dump>/`: a 1 MiB `<kind>.idx` (65,536 × 16-byte entries) and
`<kind>.dat.<part>` objects (≤ 256 MiB) of raw-DEFLATE blocks holding
sorted `key\tvalue` lines. Lookups bucket by the MBID's first four hex
digits (one range read once the index is cached in the isolate). Release
search reads the exact-title key plus up to four word keys in one parallel
round, then scores candidates with a port of `pg_trgm` `similarity()` over
diacritic-folded text (`src/snapshot_fold.tsv`), keeps scores ≥ 0.3 and
orders by score, title and MBID like the Postgres `search_sql`.

Spike scope: lookups and release search. `release_recordings`, the W6b
listings and artist/recording search return the generic 500 on this
backend.

## Gates (Operator-set) and how each is measured

| Gate | Pass | Method |
|---|---|---|
| 1 Recall | snapshot top-5 ≥ `pg_trgm` top-5 on the held-out golden set | `spike/golden.py` → `spike/pg_baseline.py` (verbatim release `search_sql`, GIN `gin_trgm_ops`) vs `snapshot_eval search` → `spike/recall.py` |
| 2 Latency | uncached lookup p95 < 250 ms; uncached search p95 < 600 ms | `spike/bench.py`: 1,000 requests at 50 concurrent per endpoint, distinct keys, no KV/edge cache; client time plus `Server-Timing` and R2 read count |
| 3 ETL | ≤ 2 h, within the 20 GB disk cap | `spike/measure.sh`: whole pipeline in `docker run --cpus 4 --memory 12g` on an exactly 20 GB filesystem |

Disclosed deviations: gate 3 runs on a GitHub runner held to the
Container standard-4 envelope, not in a Cloudflare Container (not enabled
in any environment yet); CPU speed differs. No ingest query log exists
yet, so the golden set is built from dump-sampled releases through the
ingest matcher's query path (`spike/golden.py`).

Held-out set: run 1 on seed 3599 measured 0.742 vs 0.743 (one query of
1,000). The per-query diff showed score ties ordered by byte order instead
of the collation behind `label ASC`, and folded titles tying with their
accented twins. The ranker was fixed for both (`label_sort_key`,
`exact_trigrams`) after reading that diff, so seed 3599 is no longer an
unbiased sample. Gate 1 was then pre-registered on a fresh 2,000-query
set (seed 20261107) generated by the same code.

Run 3 on seed 20261107: **gate 1 failed**, 0.730 vs 0.7315 (4 queries
only `pg_trgm` found, 1 only the snapshot found). All 4 were scene
variants of non-Latin titles whose combining marks the variant strips
(`まで` → `まて`, `λαϊκά` → `λαικα`). The fold table covered only Latin,
so those words shared no key with the indexed title and the snapshot had
no candidate. That result stands as recorded. The fold table now folds
every lowercase letter whose NFKD form carries a combining mark. Seed
20261107 has been read too, so the re-test is decided on another fresh
2,000-query set (`heldout_seed`, default 20261108); seed 3599 is still
reported for comparison. Both inspected tuning sets (1,000 at seed 3599
and 2,000 at seed 20261107) are now preserved as artifacts and excluded
from the gate set by query group (case/accent/punctuation folded). The
comparison set is excluded too, even if its requested size changes.
Different random seeds alone do not provide disjoint query groups.

The earlier 0.741 vs 0.740 result from run 42330290183 is **not valid
held-out gate evidence**: its artifacts contain 14 distinct query groups
shared with the seed-3599 tuning set even after only lowercasing and
collapsing whitespace. Gate 1 needs a new run with these exclusions; do
not reuse that pass. Gate decisions now compare integer hits on the same
query count, before rounding for display.

## Measurement limits (not production guarantees)

- Candidate retrieval intentionally reads only four word keys plus the
  exact-title key. A candidate sharing only an omitted query word is not
  fetched. An unspaced CJK typo without a shared word can also miss.
- Title posting lists are capped at 1,025 and word lists at 2,000. Fold-equivalent
  accented titles can be lost behind ASCII twins at the title cap; a
  longer typo candidate can be lost behind shorter titles at the word
  cap. These are measured recall losses, not claims of pg_trgm parity.
  Uncapping or query-aware overflow retrieval would change the bounded
  I/O design being measured, so is outside this phase-0 harness.
- Golden acceptable identities use Python `str.isalnum`, not Rust's
  Unicode Alphabetic property. Some Indic vowel marks can be removed and
  conflate same-title artists. This is a known proxy-label limitation:
  the recall figure does not establish matcher equivalence for those
  names. A production acceptance corpus needs exact matcher identities.
- Search display names are read from the curated artist TSV, not joined
  against the validated artist snapshot. Malformed supplied artist rows
  (for example a NULL sort name) can therefore disagree with lookups.
  This spike consumes this job's curated dump, not arbitrary TSV uploads;
  it is not an import-validation or malformed-data parity gate.
- The per-isolate index cache assumes one immutable R2 bucket/source per
  prefix. The Worker binds one bucket, and each native evaluation process
  reads one directory. Mixing sources under the same prefix on a thread
  is unsupported; no multi-source isolation claim is made.
- R2 reads have no application deadline. The benchmark client has a
  30-second request timeout and counts errors/timeouts against gate 2;
  the workflow also has an overall time limit. This bounds measurement,
  not Worker-side cancellation. Production use needs a server deadline.
- Memory peaks are sampled lower bounds; the last interval can be missed.

The clean-room and MetaBrainz guardrails in `AGENTS.md` still apply:
CC0 core only, no NC supplementary data or live product API reads.

## Running

- PR label `mb-snapshot-spike`: build + recall, no secrets.
- `workflow_dispatch` on `main` with `stage: true`: also uploads to
  `nntunev2-mb-snap-staging` (14-day expiry rule on `snap/`), deploys the
  token-gated `nntune-mb-snap-staging` Worker, runs the bench, then
  deletes the Worker and the objects.

Results are the run's step summary and the `mb-snapshot-spike-results`
artifact.
