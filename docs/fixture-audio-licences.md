# Fixture audio licences (CC0-only rule)

Owner decision (2026-11-03): **all NNTune development, test, CI and
staging audio must be CC0 1.0, or an equally permissive licence that
allows redistribution.** No commercial music files and no commercial
NZBs anywhere in dev/test. This page is the rule, the mechanism, and
the inventory; `.github/scripts/check_fixture_licences.py` enforces
the mechanically checkable half in CI.

## The rule

- Every audio fixture has a committed **manifest** at
  `fixtures/<tree>/<album>/manifest.json` carrying `license`
  (allow-list below), `license_url`, `source`, and one entry per file
  with `file`, `bytes` and `sha256`.
- The allow-list is exactly **`CC0-1.0`**. An "equally permissive"
  licence joins it only through an explicit licence review recorded
  in the change that adds it to the guard's `ALLOWED_LICENSES` — it
  must permit commercial redistribution (NNTune is a paid product, so
  any NC variant is out, same as the MetaBrainz rule in `AGENTS.md`).
- Audio bytes are **not committed**. They live in the R2 staging
  bucket `nntunev2-audio-staging` under the same prefix as the
  manifest's repo path (manifest `fixtures/cc0/<album>/manifest.json`,
  track file `flac/01 - x.flac` → key
  `fixtures/cc0/<album>/flac/01 - x.flac`), and tests fetch them by
  key into the gitignored `.fixture-cache/`. The one exception the
  guard permits is a small clip committed *in* its manifest's
  directory and listed by that manifest; prefer R2 anyway.
- Tests address fixture audio **through a manifest** (track position
  or listed file), never by inventing R2 keys in code.
- Runtime-synthesized audio (tones/WAV bytes generated by test code,
  e.g. `crates/nntune-test-nntp`, the web demo-media generator) is
  original test data, not a "synthetic file of unknown origin", and
  stays allowed. A checked-in audio *file* is never excused as
  "synthetic": if bytes are committed, they need a manifest.
- NZB fixtures get no exception: NZB ingest/unpack/re-post is on hold
  (see the TWO-1629 design draft), so no NZB fixture is added under
  this rule at all.

## The first fixture

`fixtures/cc0/holiznacc0-busted-guitar-jazz-66ef0593/` — HoliznaCC0,
*Busted Guitar (JAZZ)* (2022), 4 FLAC tracks (24-bit/48 kHz,
lossy-sourced from the CC0 MP3s; test only), MusicBrainz release
`66ef0593-425d-44e2-9a3a-fc136ce572b5`. The committed manifest records
the CC0 licence URL, the Free Music Archive source, MusicBrainz IDs,
per-track `sha256`, FLAC STREAMINFO MD5 and source-MP3 `sha256`. The
~133 MB of FLAC bytes are in R2 under the manifest's prefix.

## Fetching fixture audio in tests

One implementation, three entry points:

- `fixtures/cc0/fetch_fixture.py` — stdlib-only Python. Reads the
  manifest, fetches by key, verifies `bytes` + `sha256`, caches under
  `.fixture-cache/`.
- Rust: the `nntune-test-fixtures` crate (`cc0_track(position)` /
  `cc0_file(manifest, file)`).
- TS: `e2e/helpers/cc0-fixture.ts` (`cc0Track` / `cc0File`).

**Skip semantics.** When R2 read access is not configured, the helper
reports a *skip with a reason* (fetcher exit code 77), and the test
must skip — not fail. CI passes the read-only R2 repo secrets to the
jobs whose tests actually fetch (`rust-ingest`, `web-e2e`), each with
a visible fetch step that exits 0 only when the file matches the
manifest `bytes` + `sha256`; that wiring is pinned by
`.github/scripts/test_ci_fixture_secrets.py`. Fork PRs receive no
secrets, so they still skip cleanly (the licence guard below needs
no credentials and always runs). Real problems — a file/position the
manifest does not list, a network error, a hash mismatch — are
failures.

Configuration is by environment: `NNTUNE_FIXTURE_BASE_URL` (unsigned
HTTPS base the key is appended to), or S3-compatible credentials
`NNTUNE_FIXTURE_R2_ACCESS_KEY_ID` +
`NNTUNE_FIXTURE_R2_SECRET_ACCESS_KEY` with
`NNTUNE_FIXTURE_R2_ENDPOINT` or `NNTUNE_FIXTURE_R2_ACCOUNT_ID`
(bucket override `NNTUNE_FIXTURE_R2_BUCKET`, cache override
`NNTUNE_FIXTURE_CACHE_DIR`). The fetcher's docstring is the contract.

## The CI guard

`.github/scripts/check_fixture_licences.py` (in the `public-text` CI
job, with its own test suite next to it) fails on:

- any tracked audio/NZB file not listed by a valid manifest in its
  fixture directory (`tracked-audio-unlisted`);
- any `fixtures/**/manifest.json` with a missing or non-allowed
  `license`, or a missing `license_url`/`source`
  (`manifest-licence`);
- any fixture manifest whose tracks lack `file`/`bytes`/`sha256`, so
  downloads could not be verified (`manifest-shape`);
- code referencing an R2-style `fixtures/cc0/...` audio key that no
  valid manifest lists (`audio-key-unlisted`, best effort).

## Inventory at adoption (2026-11-03)

Scanned for this rule; nothing needed replacing:

- **Tracked audio/NZB files: none** (`git ls-files` over `.flac .mp3
  .ogg .opus .wav .m4a .aac .aif .aiff .alac .ape .wma .nzb`).
- **Tests loading audio from disk: none.** Existing audio-shaped test
  data is generated in memory — sine-tone WAVs in
  `crates/nntune-test-nntp`, the deterministic demo WAV in the web
  app/e2e contract, and filename literals (`track.flac`) wrapped
  around synthetic byte buffers in the NZB/par2 parser tests. All are
  original generated bytes with no third-party recording involved.
- **Former exception, retired:** the staging e2e journey used to
  rebuild a secret-held real NZB from repo secrets at runtime. That
  leg is retired under this rule — no workflow stages or ingests an
  NZB, the legs that needed an uploaded track skip by name until
  admin ingest can seed a curated track, and the retired NZB secrets
  are deleted by the operator. The dormant resolver
  (`e2e/helpers/real-nzb-fixture.ts`) stays only until the parked
  specs un-park or are deleted; it gains no new fixtures.

## Adding a fixture

1. Choose a CC0 (or reviewed-equal) recording; record where it came
   from and the licence URL.
2. Upload the audio to R2 under `fixtures/cc0/<slug>-<shortid>/`
   (operator/host step — agents do not hold bucket write keys).
3. Commit `fixtures/cc0/<slug>-<shortid>/manifest.json` in the shape
   of the first fixture's manifest, with `sha256`/`bytes` per file.
4. Point tests at it through the helpers above. The guard verifies
   the manifest, and the fetcher verifies every fetched byte.
